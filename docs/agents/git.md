# Git 操作规范

## 适用方式

本文件可用于不同仓库。分支命名和管理流程是缺少项目约定时的默认建议；用户明确要求、仓库分支保护及项目已有流程优先。提交信息采用下文的 Emoji 规范。

保护已有改动、如实报告检查结果、避免覆盖他人提交属于操作底线。本文不配置 Git hooks、CI 或远端分支保护，也不自动授予推送、合并或重写历史的权限。

## 分支命名

主分支名称以仓库实际配置为准，例如 `main` 或 `master`。工作分支建议使用 `<type>/<description>`；有关联 Issue 时，可使用 `<type>/<issue-number>-<description>`。

- `type` 优先使用下表中的常用类型；格式调整、撤销等场景可使用提交类型表中的 `style`、`revert`。分支名不携带 Emoji。
- `description` 使用简短的英文小写单词，以连字符分隔，表达本次变更目的。
- Issue 编号仅保留数字，例如 `42`。
- 用户明确指定分支名时，使用用户指定的名称。

| 类型 | 用途 | 分支示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat/42-add-skill-index` |
| `fix` | 修复缺陷 | `fix/43-correct-doc-links` |
| `docs` | 修改文档 | `docs/git-conventions` |
| `refactor` | 不改变外部行为的重构 | `refactor/simplify-skill-loader` |
| `test` | 添加或调整测试 | `test/skill-validation` |
| `perf` | 性能优化 | `perf/cache-skill-metadata` |
| `build` | 构建配置或依赖变更 | `build/update-dependencies` |
| `ci` | 持续集成配置 | `ci/check-doc-links` |
| `chore` | 其他维护工作 | `chore/remove-unused-skills` |

## Git commit 提交规范

采用 Conventional Commits 的类型、范围和破坏性变更约定，并按本项目要求在标题前添加 Emoji，确保日志可读、便于生成变更记录。配置提交校验或变更记录工具时，解析规则须支持此前缀。

### 提交粒度

- 单次提交围绕一个独立目的，如功能、修复或文档；实现该目的所需的代码、测试和文档可放在同一提交中。
- 提交前先整理改动，避免混入无关格式化或临时调试内容。
- 每个提交应可构建、可运行，方便回滚；纯文档项目执行适用的文档检查。
- 大改动拆分为多个可审查的小提交。

### 提交信息格式

```text
<emoji> <type>[(scope)][!]: <summary>

[body]

[footer]
```

- 方括号表示可选部分，不写入实际提交信息；正文与 footer 分别以空行隔开。
- Emoji 与 `type` 按下表配对；常用类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build`，其他场景按需选择。
- `scope` 使用模块或目录名，如 `app`、`data`、`scripts`、`skills`，无明确范围时省略。
- `summary` 使用中文、动词开头，长度不超过 50 字，不加句号。
- 需要时在正文补充动机、影响或迁移方式；footer 可记录关联 Issue 或破坏性变更。

### 提交类型

| 类型 | 说明 |
| --- | --- |
| `🎉 init` | 项目初始化 |
| `✨ feat` | 新功能 |
| `🐞 fix` | 错误修复 |
| `📃 docs` | 文档变更 |
| `🌈 style` | 代码格式化，不影响代码逻辑 |
| `🦄 refactor` | 代码重构，不新增功能或修复错误 |
| `🎈 perf` | 性能优化 |
| `🧪 test` | 测试相关 |
| `🔧 build` | 构建系统或外部依赖 |
| `🐎 ci` | CI 配置相关 |
| `🐳 chore` | 构建过程或辅助工具的维护，不属于上述类型的变动 |
| `↩ revert` | 撤销提交 |

示例：

```text
📃 docs(git): 补充分支命名与管理规范
🐞 fix(skills): 修正技能文档链接
🐳 chore(skills): 移除未使用的技能
```

### 破坏性变更

- 在类型及可选范围之后、冒号之前添加 `!`，例如 `✨ feat(api)!: 调整认证接口`；也可在 footer 中使用 `BREAKING CHANGE: ...`，两者可同时使用。
- 明确写出受影响范围与升级指引。

### 提交流程

1. 使用 `git status`、`git diff` 和 `git diff --cached` 确认工作区及暂存区的改动范围。已有暂存内容不属于当前任务时，保留其状态；在提交前明确隔离方式，不直接混入提交或擅自取消暂存。
2. 使用 `git add <files>` 仅添加相关文件；同一文件混有其他任务改动时，按修改块暂存。
3. 执行项目已有且适用于本次变更的检查，通过后再提交。例如，配置了 npm lint 脚本的项目执行 `npm run lint`；其他项目按实际工具链执行。检查涉及的内容须覆盖待提交版本；若格式化等检查修改了文件，重新核对并暂存相关修改，按需复查。说明未配置或未执行的检查，不将其报告为通过。
4. 使用 `git diff --cached` 核对暂存内容，再执行 `git commit -m "<符合规范的标题>"`。多行提交信息写入临时文件，通过 `git commit -F <file>` 提交。
5. 需要交付到远端时，在已授权的范围内核对推送远端和分支，再执行推送，随后按需发起 PR。

## PR 命名

- PR 标题使用同一 Emoji 提交标题格式，概括最终交付内容。
- PR 正文说明改动目的、验证结果；有关联 Issue 时附上链接或编号，仅在完整解决且托管平台支持时使用 `Closes #<number>` 等自动关闭语法。
- 使用 squash merge 时，最终提交信息也须符合上述规范。

## 分支管理

### 确定工作基线

- 优先使用用户指定或项目流程规定的目标分支；例如项目可能要求功能合入 `develop`，修复合入某个维护分支。
- 多远端仓库先根据项目文档、当前分支的跟踪配置和任务范围确定目标仓库；fork 场景中，推送远端与 PR 目标仓库可能不同。
- 无明确约定时，使用仓库默认分支。根据实际远端名称读取 `refs/remotes/<remote>/HEAD`；若本地信息缺失或可能过时，查询远端 HEAD 确认。`origin`、`main` 和 `master` 都只是常见名称，不作为固定值。
- 无远端或无法确认默认分支时，检查本地分支和项目文档；仍有歧义时，在创建分支或选择合并目标前向用户确认。
- “目标分支”指变更最终合入的分支；新分支的起点通常与其一致，但依赖其他尚未合并的工作时，可以从对应依赖分支创建，并记录依赖及预期合并顺序。

### 开始工作

- 优先沿用项目已有的分支流程；无约定时，建议使用短期工作分支，通过 PR 合入目标分支。
- 建议每个工作分支处理一个独立目标。相互依赖、共同交付的工单可以共用分支，并在 PR 中说明范围。
- 操作前检查当前分支和工作区状态，识别已有未提交改动；只暂存属于当前任务的文件或修改块。
- 需要新建工作分支时，基于已确定起点的最新状态创建；有对应远端时先获取更新。若无法获取，说明使用的本地基线及其可能过时，不将其称为最新状态。
- 继续已有任务时，优先复用其工作分支。用户明确要求使用当前分支、其他基线或直接修改主分支时，在仓库权限允许的范围内执行。
- 切换分支可能影响已有改动时，先明确这些改动的归属和保存方式；保留用户改动，不擅自丢弃或纳入本次提交。

### 同步与协作

- 有远端时，同步前先获取更新；检查分支差异，区分整合工作分支自身的远端提交与引入目标分支更新，再选择快进、合并或变基。
- merge 或 rebase 按项目约定选择。无约定时，私有且尚未推送的工作分支可变基到目标分支；已推送或多人协作的分支优先通过 merge 同步，保留共享历史。
- 冲突按双方修改意图解决，完成后运行受影响范围的检查。
- 重写已推送历史或强制推送须有用户明确授权；确需强制推送时使用 `--force-with-lease`。

### 合并与清理

- 发起 PR 前检查完整差异，确认仅包含目标范围内的改动，并完成适用的测试、类型检查或文档链接检查。
- PR 合入已确定的目标分支。合并方式遵循仓库配置和项目约定；无约定时，一个独立交付目标可采用 squash merge，需要保留逐个提交时可采用 merge，不强制统一方式。
- 创建 PR、推送和合并按用户已授权的任务范围执行；本规范本身不授予发布或合并权限。
- 确认变更已进入目标分支后，可按项目习惯清理本任务创建的临时工作分支；使用 PR 时同时核实其合并状态。长期分支继续保留。删除前确认没有合并后新增或其他未交付的提交、关联工作树、依赖该分支的未完成工作或正在使用该分支的其他任务；删除远端分支也须在授权范围内。
- squash merge 后，提交哈希变化可能使普通删除拒绝执行；此时结合 PR 合并记录和分支差异核实当前变更已完整交付，再决定是否删除，不能仅凭 PR 已合并或提交数量判断。
